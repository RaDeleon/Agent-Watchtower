# Stage 1.5 — Per-project hour tracking

**Date:** 2026-09-10
**Status:** Approved in principle (2026-09-08), specified here, pending implementation plan
**Spec it extends:** `docs/superpowers/specs/2026-09-07-claude-watchtower-design.md`
**Stage it follows:** `docs/superpowers/plans/2026-09-07-stage-1-foundation.md` (merged, PR #1)

Watchtower currently answers "how many hours have I put into Claude Code?"
Stage 1.5 answers **"into what?"** — the same active/window/prompt/cost figures,
broken out per project, all-time and over the last 30 days.

Every figure in this document was measured against the live capture DB on
2026-09-10 (2,485 sessions, 9,051 events). The tracker keeps running, so
re-measure rather than quoting these back.

---

## 1. Purpose and scope

### What it is

One row per project, over two time ranges side by side, showing: active hours,
window hours, prompts, sessions, notional cost, models used with their
thinking/effort split, and compactions with peak context pressure.

### What it is not

- **Not a second activity model.** Per-project numbers are the existing per-gap
  model grouped by a new key. The rules in `capture/rollup.sh`'s `_act` CTE do
  not change, and no part of them moves into TypeScript.
- **Not tool/skill/MCP tracking.** Declined on 2026-09-08 and still declined:
  nothing captures it (zero event payloads mention tools, skills or MCP), it
  needs a `PreToolUse` hook firing on every tool call — estimated 3-7x the
  current event volume plus a process spawn per call — and it cannot be
  backfilled. Revisit as its own stage, with its own cost/benefit argument.
- **Not lines added/removed.** Offered on 2026-09-08 and not selected. The
  columns already exist in `claude_status_snapshots`; it stays the cheapest
  thing to add later.

## 2. Decisions carried in from 2026-09-08

These were settled with the user and are **not re-opened here**. They are
restated so the implementation plan can be read against one document.

| Decision | Settled form |
|---|---|
| Project key | git toplevel path, displayed as basename |
| Non-git directories | collapse into one `Unfiled` row |
| Exclusions | `excludePaths` config; ship with `~/Library/Application Support/CodexBar/ClaudeProbe` as the only default † |
| Grouping | `projectGroups` maps repo names to a display label, applied at **read time in TypeScript** |
| Metrics per row | active h, window h, prompts, sessions, cost, models with thinking/effort split, compactions with peak context pressure |
| Time ranges | all-time **and** last 30 days, side by side |
| Storage | `rollup.sh` gains `claude_project_rollups`, one row per `(project_key, day)`; the dashboard sums rows |
| Attribution | each gap goes to the repo of the event that **ends** it |
| Sequencing | Stage 1 lands first (done), Stage 1.5 on its own branch |

† **The one place this spec extends a carried-in decision rather than
implementing it.** The default list grew from one entry to five on 2026-09-10,
after measuring: `~/.meridian` (the user's call — the app is gone) and three
patterns for Claude Code's own scratch, scratchpad and headless-temp directories,
which were not known about on 2026-09-08 and recur every session. The *rule* is
unchanged; only the shipped default list is longer. See 4.5 for the measurements.

**Grouping is labelling, not model math.** `projectGroups` never enters the SQL.
Two repos in one group stay two rows in `claude_project_rollups` and are summed
by the reader. This keeps the group definition editable without a rebuild.

**Attribution is near-lossless, re-measured.** Only **11 of 2,478** sessions
carrying a repo (0.44%) have events spanning more than one repo. The
end-of-gap rule needs no special case, and the ~0.4% it can misattribute is
below the noise floor of every figure it feeds.

## 3. The central problem: the project key does not exist yet

`claude_events` has a `repo` column already. It cannot be the project key, for
two independent reasons.

### 3.1 `repo` conflates a git repo with any old directory

`cc_repo()` returns the git toplevel's basename **or**, when the cwd is not in a
repo, the cwd's own basename. Both land in the same column, indistinguishable:

| `repo` value | actual cwd | is it a project? |
|---|---|---|
| `TheOneOS` | `/Users/you/Developer/Coding/personal/TheOneOS` | yes, a git repo |
| `you` | `/Users/you` | no, a home directory |
| `Coding` | `/Users/you/Developer/Coding` | no, a parent directory |
| `ClaudeProbe` | `~/Library/Application Support/CodexBar/ClaudeProbe` | no, an external app |

Reading `repo` as the project key silently promotes `/Users/you` to a
project with **113 sessions**. Grouping the four non-git basenames above gives
**153 sessions** that the `Unfiled` rule says must collapse into one row.

### 3.2 The toplevel cannot be computed in SQL

Resolving a cwd to its git toplevel means running `git rev-parse
--show-toplevel`. `rollup.sh` does its work in a single `sqlite3` heredoc. SQL
cannot shell out, so the mapping has to be produced **outside** the SQL and
joined in.

It is also not a pure function of the string: **15 of 75** distinct cwds are a
*subdirectory* of their toplevel, so no amount of path munging derives the key
without touching the filesystem.

### 3.3 Resolution decays — which sets the deadline

| distinct cwds (75 total) | count | resolvable today? |
|---|---|---|
| cwd **is** the git toplevel | 28 | yes |
| cwd is **below** a toplevel | 15 | yes |
| not a git repo | 17 | n/a — `Unfiled` by rule |
| **directory no longer exists** | **15** | **no, permanently** |

Those 15 vanished directories account for **51 sessions and 292 events**. They
can never be resolved, because the evidence was on disk and the disk moved on.
The number only grows: every project deleted, renamed or moved before its cwd is
resolved becomes permanently unattributable.

**This is the argument for a persistent cache rather than resolution on demand.**
Resolve each cwd once, while it still exists, and store the answer forever.

## 4. Design

### 4.1 Capture the toplevel at capture time — it is already free

`cc_repo()` computes the toplevel path and then throws it away:

```bash
cc_repo() {
  local d="$1" top
  top="$(git -C "$d" --no-optional-locks rev-parse --show-toplevel 2>/dev/null)"
  if [ -n "$top" ]; then basename "$top"; else basename "$d"; fi
}
```

The subprocess has already run. Keeping `$top` instead of discarding it costs
**nothing** — no extra `git` call, no extra process, no measurable change to hook
latency. Add a sibling that returns the path, and have the hook write it:

```bash
# Git toplevel PATH for a cwd, or empty when the cwd is not in a repo.
# Deliberately NOT basename'd: the path is the project key, the basename is
# only how it is displayed. Empty is meaningful -- it means Unfiled.
cc_project_path() {
  local d="$1"
  [ -z "$d" ] && { printf ''; return; }
  git -C "$d" --no-optional-locks rev-parse --show-toplevel 2>/dev/null
}
```

New nullable column `project_path` on `claude_events`, `claude_sessions` and
`claude_status_snapshots`; `CC_SCHEMA_VERSION` goes to 2. Nullable and additive,
so the existing 9,051 rows stay valid and `cc_init_db`'s marker handles the
migration exactly as it handles a fresh install.

**Constraint this must respect:** `hook.sh` and `snapshot.sh` exit 0 silently on
any failure. A cwd that is not a repo, a `git` that is missing, a directory that
vanished mid-session — all yield empty, never an error, never stdout.

### 4.2 Backfill history through a cache table

Going forward, 4.1 is sufficient. It does nothing for the 2,485 sessions already
captured, and the 15-vanished-cwd number says waiting makes it worse.

```sql
-- cwd -> git toplevel, resolved once and kept. A row here is a durable answer
-- to a question the filesystem may stop being able to answer: a project deleted
-- next week keeps the attribution it had this week.
CREATE TABLE IF NOT EXISTS claude_project_paths (
  cwd           TEXT PRIMARY KEY,
  project_path  TEXT,              -- NULL: resolved, and it is NOT a repo -> Unfiled
  resolved_at   INTEGER NOT NULL,
  source        TEXT NOT NULL      -- 'git' | 'gone' | 'capture'
);
```

`source` is what keeps the three "no project" cases apart, which `repo` alone
cannot do:

- `git` — resolved against a real repo. `project_path` is the toplevel.
- `capture` — written by the hook from `cc_project_path` (4.1).
- `gone` — the directory did not exist at resolution time. See 4.4.

**Resolution step**, in `rollup.sh`, in bash, *before* the SQL heredoc:

1. `SELECT DISTINCT cwd FROM claude_events WHERE cwd NOT IN (SELECT cwd FROM claude_project_paths)`
2. For each, run `cc_project_path`; insert `git` (with a path), `git` with NULL
   (exists, not a repo), or `gone`.
3. The SQL heredoc then `LEFT JOIN`s `claude_project_paths` on `cwd`.

**Cost.** Bounded by *new* cwds per run, not total. Today's steady state is 0-1
new cwds per `SessionEnd`, so the common case is one `SELECT` returning nothing.
The first run after upgrade resolves 75. At roughly 5ms per `git rev-parse`
that is a one-time ~0.4s against the current ~0.18s rebuild — acceptable once,
and it must not run under the `SessionEnd` hook path if it exceeds that. If it
does, gate the first bulk resolve behind an explicit `rollup.sh --resolve`.

### 4.3 Project key and display name

```
project_key  = claude_project_paths.project_path     when non-NULL
             = '(unfiled)'                           otherwise
display_name = basename(project_key)                 -- read time, TypeScript
```

`project_key` is a full path, so two repos with the same basename in different
parents stay distinct rows and only collide in the *display*, where
`projectGroups` is the tool for saying whether that is intended.

Two reserved keys are parenthesised so they cannot collide with a real toplevel
path, which is always absolute: `(unfiled)` for a cwd that is not in a repo or
cannot be resolved, and `(excluded)` for a cwd matching `excludePaths` (4.5).

### 4.4 The `gone` case — decided 2026-09-10: fold into `Unfiled`

15 cwds can never be resolved. The 2026-09-08 decisions did not cover them, so
this was specified as open, with a recommendation to preserve them under a
`gone:` key. **Measuring the population reversed that recommendation.**

| class | cwds | sessions | events | active h |
|---|---|---|---|---|
| `~/.meridian` | 1 | 39 | 190 | 0.35 |
| ephemeral scratch/temp | 4 | 5 | 16 | 0.02 |
| genuinely moved projects | 10 | 7 | 86 | — |

The case for preserving the bucket rested almost entirely on `.meridian`'s 190
events looking like a real project. Two things killed it:

- **`.meridian` is out.** The app is no longer installed; the user's call on
  2026-09-10 is that its history need not be preserved. It moves to
  `excludePaths` (4.5), not to a `gone:` key.
- **The four ephemeral cwds were never projects** — Claude Code's own scratchpad,
  headless temp dir and scratch-workspaces. They also move to `excludePaths`.

What is left is **10 cwds, 7 sessions, 86 events — 0.28% of all sessions**: real
directories that were moved or renamed (a `Claude Custom/Skills` tree that has
since been spelled three ways, two `~/Downloads` checkouts). At that volume a
third bucket, a reserved key prefix and a UI caveat cost more than they explain.

**Decision: fold unresolvable cwds into `Unfiled`.** One rule, no third bucket.
The rule is honest about what it means — "we cannot attribute this" — and the
cache in 4.2 is what stops the number growing, by resolving cwds while their
directories still exist. Revisit only if `Unfiled` ever grows enough to hide
something worth drilling into.

### 4.5 Exclusions

`excludePaths` is a list of path prefixes and glob-ish patterns, applied in the
resolution step (4.2). A matching cwd resolves to the reserved project key
`(excluded)`.

**Excluded work is keyed, not dropped.** An earlier draft of this spec dropped
excluded rows from the rollup entirely, which quietly broke the reconciliation
identity in section 7: every second the daily rollup counts has to be findable
in some per-project row, or the two tables cannot be checked against each other.
Writing excluded work to a reserved key keeps the identity exact and
unconditional, and the reader simply hides that key. It also keeps the choice
reversible: dropping an entry from `excludePaths` and rebuilding brings the
history back, because nothing was destroyed.

**Exclusions never touch lifetime hours or rank.** `claude_daily_rollups` and
`claude_rank_progress` are unchanged by this stage. `excludePaths` decides what
the per-project view *shows*, not what the tracker *counts*.

Shipping defaults, all measured 2026-09-10:

```json
{
  "excludePaths": [
    "~/Library/Application Support/CodexBar/ClaudeProbe",
    "~/.meridian",
    "~/Library/Application Support/Claude/scratch-workspaces",
    "/private/tmp/claude-*",
    "/private/var/folders/*/T/cc-headless-*"
  ]
}
```

| pattern | why | sessions | active h |
|---|---|---|---|
| `CodexBar/ClaudeProbe` | external status-bar app polling Claude Code | 1,792 (**72% of all sessions**) | 0.00 |
| `~/.meridian` | app no longer installed; user's call, 2026-09-10 | 39 | 0.35 |
| `Claude/scratch-workspaces` | Claude's own scratch dirs, never a project | 2 | 0.02 |
| `/private/tmp/claude-*` | Claude Code session scratchpads | 2 | (in the 0.02) |
| `cc-headless-*` | headless-run temp dirs | 1 | (in the 0.02) |

Together they account for **~0.37 of ~197 active hours (0.19%)** and **1,836 of
2,485 sessions (74%)**. That asymmetry is the entire argument for excluding
them: they are almost pure session-count noise carrying no real time, so leaving
them in makes every per-project session count meaningless while removing them
costs a rounding error of hours.

The last three patterns are **recurring, not historical** — Claude Code mints a
new scratchpad per session (last seen 2026-09-09), so these must be patterns
rather than the literal paths observed today. Pattern matching is `case`-style
globbing in the resolution step, not a regex engine.

### 4.6 Splitting a session across projects

Attribution is per gap, so a session that changes directory mid-flight splits
across two project keys. **20 of 2,478 sessions (0.81%)** touch more than one
cwd. Small, but not zero, and the reconciliation identity in section 7 has to
survive them.

Time splits cleanly. Session-level scalars do not: a session counted as 1 in
each of two project rows makes `SUM(sessions_count)` exceed
`claude_daily_rollups.sessions_count`, and duplicating the latest snapshot's
tokens into both rows is the same fan-out shape that already doubled every
daily aggregate once. Two classes of column, two rules:

| Class | Columns | Rule |
|---|---|---|
| **Per gap** | `active_ms`, `window_ms`, `idle_ms` | Split by the project of the event that **ends** the gap. Sums exactly, by construction. |
| **Per session** | `sessions_count`, `prompts`, `compacts`, `clears`, `subagents`, `tokens_*`, `cost_usd`, `avg_context_pct`, `peak_context_pct` | Assigned **whole** to the session's dominant project, and to no other. |

**Dominant project** = the project key holding the most `active_s` within that
session. Ties break by the project of the session's **last** event, ordered
`ts, id` — the same ordering discipline the activity model already uses, and for
the same reason: `ORDER BY ts` alone leaves ties to an order SQLite does not
promise.

This keeps every column of the identity exact rather than approximately right,
which matters because the identity is the only thing standing between this
design and a second activity model growing quietly in the per-project path.

It also means a per-project **row count is not a session count** in the strict
sense for the 0.81%: their time appears under both projects while their tokens
and cost appear under one. That is the honest trade, and the alternative —
duplicating scalars — is the bug.

## 5. Schema: `claude_project_rollups`

```sql
-- Derived per-project daily history. Same rebuild discipline as
-- claude_daily_rollups: DELETE + re-INSERT inside the same transaction, under
-- .bail on, so a failure mid-rebuild cannot commit a half-built table.
CREATE TABLE IF NOT EXISTS claude_project_rollups (
  project_key            TEXT NOT NULL,
  day                    TEXT NOT NULL,     -- YYYY-MM-DD, local, session START day
  display_name           TEXT,              -- basename at resolution time, for a vanished path
  active_ms              INTEGER DEFAULT 0,
  window_ms              INTEGER DEFAULT 0,
  idle_ms                INTEGER DEFAULT 0,
  sessions_count         INTEGER DEFAULT 0,
  prompts                INTEGER DEFAULT 0,
  compacts               INTEGER DEFAULT 0,
  clears                 INTEGER DEFAULT 0,
  subagents              INTEGER DEFAULT 0,
  tokens_in              INTEGER DEFAULT 0,
  tokens_out             INTEGER DEFAULT 0,
  tokens_cache_read      INTEGER DEFAULT 0,
  tokens_cache_creation  INTEGER DEFAULT 0,
  cost_usd               REAL    DEFAULT 0,
  models_json            TEXT,              -- {"model": {"sessions":N,"thinking":N,"effort":{...}}}
  peak_context_pct       REAL    DEFAULT 0,
  avg_context_pct        REAL    DEFAULT 0,
  updated_at             INTEGER,
  PRIMARY KEY (project_key, day)
);
CREATE INDEX IF NOT EXISTS idx_projroll_day ON claude_project_rollups(day);
```

**`window_ms`, not `total_session_ms`.** `claude_daily_rollups` calls this
column `total_session_ms` and it has caused a naming confusion with
`claude_sessions.duration_ms` — the phantom column that sums to 10,370 hours
against 196h of real active time. The new table names it after the only valid
source. The old column keeps its name; renaming it is a Stage 2 migration, not
a Stage 1.5 side effect.

**Both time ranges come from this one table.** All-time is every row; last 30
days is `WHERE day >= date('now','localtime','-29 days')`. No second table, no
second rebuild, no window-specific model.

### The day boundary, inherited deliberately

A session is attributed to its **local start day**, whole. A session running
23:50 to 00:20 books all of its time to the start day. That rule is already in
`rollup.sh`, is now pinned by the `crosses-midnight` fixture (added
2026-09-10), and applies unchanged here. Per-project rows inherit it, so a
per-project daily chart and the existing daily chart agree by construction.

## 6. Reader

TypeScript reads `claude_project_rollups` and does exactly three things:

1. **Sum** rows for the selected range.
2. **Apply `projectGroups`** — map `display_name` to a group label, sum within
   the label. Pure labelling.
3. **Format** — hours from ms, currency, percentages.

No gap logic, no caps, no day bucketing, no re-derivation from raw tables. The
Global Constraint stands: the activity model lives in `capture/rollup.sh` and
nowhere else, and `tests/capture-scripts.test.ts` now fails if a model constant
appears outside it.

```jsonc
// watchtower.config.json
{
  "projectGroups": {
    "VPS":       ["vps-host-a", "vps-host-b", "vps-host-c"],
    "client":    ["client-site.com", "client-api", "client-admin"]
  },
  "excludePaths": [
    "~/Library/Application Support/CodexBar/ClaudeProbe",
    "~/.meridian",
    "~/Library/Application Support/Claude/scratch-workspaces",
    "/private/tmp/claude-*",
    "/private/var/folders/*/T/cc-headless-*"
  ]
}
```

`loadConfig` gains both keys with the same precedence as everything else
(defaults < file < env) and the same loud-failure posture — an `excludePaths`
that is not an array of strings throws, exactly as an invalid `coach.mode` now does.

## 7. Testing

Fixture-driven, no mocks, real `bash`/`sqlite3`/`jq` — same discipline as
Stage 1, which is what caught five real bugs there.

**New fixture scenarios** (`tests/fixtures/make-fixture.sh`):

Named by behaviour here; the implementation plan consolidates them into four
fixtures (`four-projects`, `mixed-projects-one-day`, `session-spans-two-projects`
and the existing `crosses-midnight`) and carries the mapping.

| Scenario | Asserts |
|---|---|
| `two-projects-one-day` | two toplevels on one day produce two rows that sum to the single-project total; neither doubles |
| `subdir-of-repo` | a cwd *below* a toplevel keys to the toplevel, not to itself — the 15-of-75 case |
| `non-git-cwd` | a non-repo cwd keys to `(unfiled)`, not to its basename — the `/Users/you` case |
| `excluded-path` | an `excludePaths` cwd keys to `(excluded)`, does not inflate `Unfiled`, and is hidden by the reader |
| `reconciles-with-daily` | a day holding excluded + unresolvable + two real projects reconciles exactly against `claude_daily_rollups` |
| `session-spans-two-repos` | the gap books to the repo of the event that **ends** it |
| `gone-cwd` | an unresolvable cwd keys to `(unfiled)`, per the 4.4 decision |
| `crosses-midnight` (exists) | per-project rows book to the start day, agreeing with `claude_daily_rollups` |

**The reconciliation test, which is the important one:**

> For every day, `SUM(claude_project_rollups.active_ms)` over **every** key —
> `(unfiled)` and `(excluded)` included — equals `claude_daily_rollups.active_ms`
> for that day. Same for `window_ms`, `prompts` and `sessions_count`.

Both tables are built from the same `_act` CTE in the same rebuild. If they ever
disagree, the per-project path has grown model logic of its own — the exact
failure this design exists to prevent.

Two properties make this test worth writing:

- **It is unconditional.** Because excluded work is keyed rather than dropped
  (4.5), every second the daily rollup counts is findable in some per-project
  row. A test that had to subtract an "excluded delta" first would be a test of
  the arithmetic in the test.
- **It is per day, not on the total.** Summed across all days, two days wrong in
  opposite directions cancel and the identity still holds.

Assert it against a fixture that contains at least one excluded cwd, one
unresolvable cwd and two real projects on the same day — otherwise the identity
holds trivially.

Two guards from Stage 1 carry forward unchanged. Constants stay pinned by count
in `rollup.sh` and are forbidden elsewhere. Fixtures fail loudly through
`fx_sql` — a typo'd column aborts the build instead of silently producing an
empty DB and a green assertion.

## 8. Install, migration and lockstep

**Schema.** `CC_SCHEMA_VERSION` 1 → 2. `cc_init_db`'s `.schema-v<N>` marker
means the new tables and columns are applied on first run after install, and
`tests/capture-scripts.test.ts` already pins `CC_SCHEMA_VERSION` against
`lib/config.ts`'s `schemaVersion`, so the two cannot drift.

**Rollups are regenerable.** `claude_project_rollups` derives entirely from raw
tables; dropping it loses nothing. `claude_project_paths` is the exception — it
is a *cache of a fact the filesystem may forget*, and must survive a rebuild.
Never `DELETE` it in the rebuild transaction.

**The three-place lockstep still applies.** The model exists in
`capture/rollup.sh` (source of truth), `~/.claude/claude-usage-rollup.sh` (the
installed copy) and `TheOneOS/lib/claude-hours/` (recomputes from raw tables).
Stage 1.5 adds a table; it must not change a single activity-model rule. If a
rule does change, prove lockstep the documented way: extract `PER_SESSION_SQL`
from `hours.ts`, run it against the same DB copy the shell rollup just
processed, and require an exact match.

**Testing safety, unchanged and non-negotiable.** Never run `install.sh` without
`CLAUDE_DIR` pointed at a temp dir. Never test against the live DB: copy with
`sqlite3 .backup` (never `cp` — it is WAL) and point `THEONE_DB_PATH` at the copy.

## 9. Implementation order

1. `cc_project_path()` in `lib.sh`; `project_path` columns; schema v2. Test:
   a session in a subdirectory of a repo records the toplevel.
2. `claude_project_paths` + the resolution step in `rollup.sh`, with the
   `excludePaths` filter. Test: the four resolution outcomes.
3. `claude_project_rollups` + its INSERT in the existing rebuild transaction.
   Test: the reconciliation identity, per day.
4. Config: `projectGroups`, `excludePaths`, loud validation. Test: precedence
   and rejection of malformed values.
5. Reader + display, all-time and 30-day. Test: grouping is applied after the
   sum and changes no underlying row.

Steps 1-3 are the stage. 4-5 are only useful once 3 reconciles.

Nothing in this order is blocked on an open decision: 4.4 was settled on
2026-09-10 and 4.5's defaults are measured, so step 2 can start as soon as the
plan is written.

## 10. Open items

- **The headline session count is 74% noise.** 1,836 of 2,485 sessions are
  excluded work, overwhelmingly ClaudeProbe. `claude_daily_rollups.sessions_count`
  and `claude_rank_progress.sessions_count` still count them, so "2,485 sessions"
  overstates real usage by ~4x. Active hours and rank are NOT affected (0.19%),
  which is why this is not urgent — but a session count nobody should quote is
  worth fixing in Stage 2, deliberately and with the rank implications spelled out.
  Out of scope here: this stage must not change lifetime hours or rank.
- **Purging `~/.meridian` from the raw tables.** Excluding it hides it
  reversibly, which is what this spec does. An actual `DELETE` of the 190 raw
  events is irreversible and was not requested; if wanted, do it as its own
  reviewed change with a `sqlite3 .backup` taken first.
- **First-run resolution cost.** ~75 `git` calls once. Measure it against the
  ~0.18s rebuild budget before letting it run on the `SessionEnd` hook path; if
  it does not fit, gate the bulk resolve behind `rollup.sh --resolve`.
- **`total_session_ms` naming.** The new table uses `window_ms`. Renaming the
  old column to match is a Stage 2 migration, deliberately not done here.
- **Tool/skill/MCP tracking.** Still declined. Its own stage, its own argument.
- **Lines added/removed.** Still not selected. The columns already exist in
  `claude_status_snapshots`; adding it later is cheap.
